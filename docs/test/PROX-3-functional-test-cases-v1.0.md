# autohunt 功能测试用例集 v1.0（S2b，对应 G1 设计基线）

> 阶段：S2b 功能用例（G2 汇合门禁输入之一）。作者：@Tester-鲁智深。

## 1. 编号与字段约定

- 用例 ID：`TC-<模块>-<序号>`，模块：RSM 简历 / CFM 确认流 / SEC 安全负例 / SUB 提交回写 / DUP 重复投递 / SM 状态机 / MAIL 邮箱事件 / STA 统计 / AUTH 邮箱授权 / EDGE 空异常态。
- 每条字段：优先级（P0=AC/BR 直接对应，P1=重要辅助）、类型（正向/负例/边界）、前置条件、步骤、预期结果、追溯（AC/FR/BR/§12/DESIGN-ID/技设§）。
- "Agent 侧操作"指以 Agent Bearer key 调系统 API（模拟外部 Agent CLI）；"UI 侧"指 Web 界面操作（自动化时可用 UI session 调 API 模拟）。

## 3. 用例正文

### 3.1 简历管理（AC-1，FR-1/2/3，D-02/D-03）

**TC-RSM-01**（P0·正向）规范 PDF 全字段解析
- 前置：已启动应用，无简历。
- 步骤：D-02 上传一份字段齐备的样例 PDF（姓名/电话/邮箱/教育/实习/技能/证书俱全）。
- 预期：卡片状态 `解析中` → `解析完成`；结构化档案各字段与 PDF 内容一致；必填项无缺失标记。
- 追溯：AC-1、FR-1/2。

**TC-RSM-02**（P0·正向）部分字段缺失可手动补全
- 步骤：上传缺少"技能/获奖"与一条教育经历的 PDF → 进入 D-03，补全缺失字段并保存。
- 预期：卡片显示 `部分字段缺失`（warning badge + 缺失字段数）；缺失字段输入框带 warning 描边与"待补全"角标，填写后角标消除；显式「保存」后持久化，重新进入值不变。
- 追溯：AC-1、FR-2、§10.1。

**TC-RSM-03**（P0·负例）解析失败降级手动编辑
- 步骤：上传扫描件/损坏 PDF。
- 预期：卡片 `解析失败`（danger badge + 失败原因）+ CTA「手动填写」进入 D-03 空白表单；其余功能（看板/日程等）不受阻塞。
- 追溯：AC-1、§12 异常·简历解析失败。

**TC-RSM-04**（P0·正向）多版本与默认简历
- 步骤：上传 v1、v2 两份简历；将 v2 设为默认；Agent 侧 `GET /profile`（不带 resume_id）。
- 预期：版本列表按导入排序、默认 badge 在 v2；API 缺省返回 v2 档案；带 `resume_id=v1` 返回 v1。
- 追溯：FR-1/20、技设 §3.2。

**TC-RSM-05**（P1·边界）被引用简历禁止删除
- 前置：简历 v1 已被 N≥1 条投递引用。
- 步骤：D-02 尝试删除 v1。
- 预期：删除按钮置灰 + tooltip"已被 N 条投递引用"；数据未被删除，投递详情仍可回溯该版本（FR-3）。
- 追溯：FR-3、D-02、§5 禁用态。

**TC-RSM-06**（P1·边界）上传文件类型/大小校验
- 步骤：分别上传 `.docx` 文件、>10MB 的 PDF。
- 预期：均被拒绝并给出明确原因提示；不产生版本记录。
- 追溯：D-02（仅 .pdf，≤10MB）。

**TC-RSM-07**（P1·边界）档案邮箱默认值规则
- 步骤：① 绑定求职邮箱后创建档案，email 留空；② 修改档案 email 为其他值；③ 换绑求职邮箱后再查档案 email。
- 预期：① 自动回填为已绑定求职邮箱；② 保存为用户值；③ 保持用户修改值，不再跟随绑定变化。
- 追溯：§10.1 注、技设 v1.1 §3.2。

**TC-RSM-08**（P1·边界）未保存改动保护
- 步骤：D-03 修改字段不保存，尝试离页。
- 预期：二次确认弹窗；确认离开则丢弃，取消则停留。保存前 Agent 侧 `GET /profile` 读到的是旧值（半完成状态不外泄）。
- 追溯：D-03（显式保存语义）、FR-20。

### 3.2 确认流正向（AC-2，FR-20/21/22，BR-1，D-06）

**TC-CFM-01**（P0·正向）端到端：修改字段后确认，Agent 读回修改后值
- 步骤：① UI 录入岗位并创建投递；② Agent 侧 `GET /profile` 拉档案 → `POST /confirmations`（含字段-值快照、request_id）；③ UI：首页待确认区出现该任务（置顶卡 + 导航红点计数 +1）→ 进 D-06，将"电话"改为新值；④「确认并允许提交」→ 二次确认弹窗确认；⑤ Agent 侧 `GET /confirmations/{id}`。
- 预期：③ 对照表逐行展示快照值/确认值，修改行高亮 + "已修改" badge；④ 弹窗文案明示"确认后外部 Agent 将按以上确认值提交…不可撤销"；状态变 `已确认`；⑤ 返回 `confirmed_fields` 中电话为**修改后值**，且携带 `submit_token` 与 `expires_at`。
- 追溯：AC-2（核心路径）、FR-20/21/22、技设 §3.4 步骤 1-3。

**TC-CFM-02**（P0·正向）无修改直接确认
- 步骤：同 TC-CFM-01 但不改任何字段。
- 预期：改动摘要提示"0 处修改"；确认后 Agent 读到的 confirmed_fields 与快照一致；submit_token 正常签发。
- 追溯：AC-2、FR-22。

**TC-CFM-03**（P0·负例）驳回流程终止
- 步骤：D-06「驳回」→ 弹窗中留空原因提交；再填写原因提交；Agent 侧查询。
- 预期：原因为空不可提交（必填校验）；提交后状态 `已驳回`；Agent 读到 `{status:已驳回, reason}`，无 submit_token；该确认单不可再操作（只读留档）。
- 追溯：FR-22、§10.3、技设 §3.4 步骤 3。

**TC-CFM-04**（P0·正向）许可闸门可视化
- 步骤：确认任务在 `待确认` 与 `已确认` 两状态分别查看 D-06 右上区。
- 预期：待确认显示锁形图标 + "未确认 · 系统不会放行提交"；确认后变为 "已确认 · 提交许可已放行给 Agent"。
- 追溯：AC-3 的用户可见面、D-06。

**TC-CFM-05**（P1·边界）必填确认为空校验
- 步骤：将某必填字段（对照 §10.1 必填项）的确认值清空后点确认。
- 预期：该行行内标红，页面锚点滚动至第一处错误；不产生状态变更。
- 追溯：D-06 校验反馈。

**TC-CFM-06**（P1·边界）快照空值补录
- 步骤：Agent 创建的快照中某字段为空。
- 预期：快照列显示"（Agent 未填写）"占位；确认值可手动补录；确认后 Agent 读到补录值。
- 追溯：D-06、AC-2。

**TC-CFM-07**（P1·正向）修改行还原
- 步骤：修改多行后逐行点「还原」。
- 预期：对应行恢复快照值、高亮与 badge 消除；确认摘要计数同步减少。
- 追溯：D-06。

**TC-CFM-08**（P0·边界）终态任务只读留档
- 步骤：对已确认/已驳回/已超时关闭三类任务再次进入 D-06。
- 预期：整页只读（快照 + 修改值 + 结果留档可见），顶部终态 badge；无任何可编辑/可操作控件。
- 追溯：§10.3、D-06、§5 禁用态。

**TC-CFM-09**（P0·正向）手动关闭待确认任务
- 步骤：D-06「关闭任务」→ 确认弹窗；Agent 侧查询。
- 预期：状态 `已超时关闭`；Agent 读到该状态且无 token，流程终止；首页待确认计数 -1。
- 追溯：§12 异常·确认任务长期未处理、§10.3。

**TC-CFM-10**（P0·回归）持续挂起、无自动超时
- 步骤：创建待确认任务后不做任何操作，（测试环境可将时钟/创建时间拨快）模拟超过 72h。
- 预期：任务**仍然挂起展示**（挂起时长 >24h 变 warning 文案），状态不自动变更；仅用户手动关闭才进入 `已超时关闭`。
- 追溯：技设 v1.1 §3.4 步骤 6（B-3 修复，对齐 PRD §12）——防 72h 自动超时回归。

### 3.3 AC-3 负例矩阵（BR-1，技设 §3.4/§9 —— 全部为 P0 负例）

> 目标：证明"确认状态未达已确认前系统不提供可提交许可，且系统内不存在任何未经确认即标记已投递的路径（含异常重试）"。以下每条独立执行，任一失败即 AC-3 FAIL。

**TC-SEC-01** 待确认状态查询无许可
- 步骤：创建确认单后（不确认）Agent `GET /confirmations/{id}`。
- 预期：响应仅含 `status:待确认`，**无** submit_token / confirmed_fields 等许可与结果字段。

**TC-SEC-02** 创建确认响应不携带许可
- 步骤：`POST /confirmations` 检查 201 响应体。
- 预期：仅 `confirmation_id, status`；无任何 token 类字段。

**TC-SEC-03** 伪造 token 回写
- 步骤：编造随机字符串作 submit_token 调 `POST /applications/{id}/submit-result`。
- 预期：403 `PERMIT_INVALID`；投递状态不变；无 status_history 写入。

**TC-SEC-04** 过期 token 回写
- 步骤：确认取得 token 后，人为令 token 过期（测试钩子或等待 TTL），再回写。
- 预期：403；确认单状态保持 `已确认`；查询时 submit_token 字段为空。
- 追溯：技设 v1.1 §3.4 步骤 3/5。

**TC-SEC-05** 已消费 token 重复回写
- 步骤：正常回写成功一次后，用同一 token 再回写。
- 预期：第二次 403（一次性语义）；台账无重复记录。

**TC-SEC-06** 无 token 回写
- 步骤：submit-result 请求不带 submit_token 字段。
- 预期：403 `PERMIT_REQUIRED`。

**TC-SEC-07** Agent 直调 PATCH 推进"已投递"（绕过确认流）
- 步骤：Agent Bearer 调 `PATCH /applications/{id}` `{status:"已投递"}`，不携带 Permit/submit_token。
- 预期：403/拒绝；状态不变。再携带伪造 token 重试，同样 403。
- 追溯：技设 §3.4 步骤 4（绕过路径封堵）。

**TC-SEC-08** Agent 直调确认端点
- 步骤：Agent Bearer 调 `POST /confirmations/{id}/confirm`。
- 预期：403 `FORBIDDEN`；状态不变；不签发 token。
- 追溯：技设 v1.1 §3.4 步骤 2（B-1，BR-1 最后一道门）。

**TC-SEC-09** Agent 直调驳回端点
- 步骤：Agent Bearer 调 `POST /confirmations/{id}/reject`。
- 预期：403 `FORBIDDEN`。

**TC-SEC-10** Agent 直调重新放行端点
- 步骤：确认单已确认且 token 过期后，Agent Bearer 调 `POST /confirmations/{id}/reissue`。
- 预期：403 `FORBIDDEN`；不签发新 token（重新放行永远是人动作）。
- 追溯：技设 v1.1 §3.4 步骤 5。

**TC-SEC-11** 异常重试幂等
- 步骤：Agent 以同一 `request_id` 连续 `POST /confirmations` 两次（模拟超时重试）。
- 预期：第二次返回**首个** confirmation（同 id），不产生重复确认任务；首页待确认计数只 +1。
- 追溯：技设 §3.4 步骤 1、AC-3"含异常重试路径"。

**TC-SEC-12** token 跨确认单使用
- 步骤：确认单 A、B 均已确认；用 A 的 token 回写 B 的投递。
- 预期：403（token 绑定 confirmation_id + confirmed_fields 哈希）。
- 追溯：技设 §3.4 步骤 2/4。

**TC-SEC-13** 无凭证/无效凭证/已吊销凭证
- 步骤：① 不带 Authorization；② 错误 key；③ 吊销后的 key —— 分别调任一 Agent 端点。
- 预期：①② 401 `UNAUTHORIZED`；③ 吊销即时生效，401；`GET /keys` 列表永不回显完整 key（仅前缀）。
- 追溯：FR-25、技设 §3.1。

**TC-SEC-14** Agent 自签发/自吊销密钥
- 步骤：Agent Bearer 调 `POST /keys` 与 `DELETE /keys/{id}`。
- 预期：均 403 `FORBIDDEN`（密钥管理仅 UI session）。
- 追溯：技设 §3.1。

### 3.4 提交结果回写（AC-4，FR-23/24，技设 §3.4 步骤 4/5）

**TC-SUB-01**（P0·正向）回写成功自动推进
- 步骤：确认后 Agent 携合法 token 回写 `{result:"success"}`。
- 预期：投递状态推进为 `已投递`，status_history 来源 = Agent 回写；D-06 转结果视图：success 横幅 + 提交时间；token 被消费。
- 追溯：AC-4、FR-23。

**TC-SUB-02**（P0·正向）回写失败保留快照
- 步骤：回写 `{result:"failed", fail_reason:"官网验证码拦截"}`。
- 预期：fail_reason 与字段快照完整保留；投递状态**不推进**；D-06 danger 横幅 + 原因 + 快照保留区 + CTA「转人工完成」（打开 JD 链接新标签页）。
- 追溯：AC-4、FR-24。

**TC-SUB-03**（P0·正向）失败后转人工闭环
- 步骤：TC-SUB-02 后，用户按引导人工到官网完成投递，回 D-05 手动更新状态为 `已投递` 并写备注。
- 预期：手动推进无需 token（用户即确认者）成功；状态历史记录该手动变更与备注；D-05「确认记录」中该次确认流全程（快照/修改/失败原因/人工收尾）可回溯。
- 追溯：FR-24、技设 §3.4 步骤 4。

**TC-SUB-04**（P0·负例）B-2 闭环：过期 → 重新放行 → 回写成功
- 步骤：① 确认后令 token 过期；② Agent 回写（预期 403）；③ Agent 查询确认单；④ UI 点「重新放行」；⑤ Agent 再次查询并携新 token 回写。
- 预期：② 403；③ submit_token 字段为空；④ reissue 成功（UI session），confirmed_fields 不变、重置 TTL；⑤ 读到新 token，回写成功、投递推进 `已投递`。
- 追溯：技设 v1.1 §3.4 步骤 5、§9 AC-4 闭环断言（G1 评审 B-2）。

**TC-SUB-05**（P0·负例）已回写成功不可重新放行
- 步骤：TC-SUB-01 完成后调 `POST /confirmations/{id}/reissue`（UI session）。
- 预期：拒绝（409 或 403，以契约为準）；不签发新 token。
- 追溯：技设 v1.1 §3.4 步骤 5。

**TC-SUB-06**（P0·负例）失败回写消耗 token 后的恢复
- 步骤：TC-SUB-02（失败回写已消费 token）后，Agent 再次回写；然后 UI「重新放行」。
- 预期：再回写 403（token 已消耗）；重新放行允许并签发新 token（v1.1 明确含"回写失败被消耗"场景）；Agent 携新 token 可再次尝试提交回写。
- 追溯：技设 v1.1 §3.4 步骤 5。

### 3.5 重复投递提示（BR-3，D-04）

**TC-DUP-01**（P0·正向）录入提示不拦截
- 前置：已存在公司 A + 岗位 X 的投递（创建于 3 日前）。
- 步骤：D-04「录入岗位」再次填写公司 A + 岗位 X 并提交。
- 预期：表单内出现 warning 提示条"已有该公司的同岗位投递（创建于 3 日前），确认重复投递？"；**不拦截**，确认后创建成功，看板出现两条记录。
- 追溯：BR-3。

**TC-DUP-02**（P0·正向）API 侧重复语义
- 步骤：Agent/UI session `POST /jobs` 提交同公司同岗位。
- 预期：200 + 响应含 `duplicate_of`（指向已有记录），非 409；记录按确认创建。
- 追溯：技设 §3.3、BR-3。

**TC-DUP-03**（P1·边界）提示的匹配边界
- 步骤：① 同公司不同岗位；② 同岗位不同公司；③ 公司名大小写/全半角差异（如 "字节" vs "字节跳动"）。
- 预期：①② 无提示；③ 按契约的匹配口径判定（若精确匹配则无提示）——记录实际行为供 BR-3 口径评审，不得出现崩溃或错误拦截。
- 追溯：BR-3。

### 3.6 状态机（BR-10/11，技设 §5，D-04/D-05）

**TC-SM-01**（P0·正向）主链全路径流转
- 步骤：UI 手动沿 `待投递→已投递→笔试→面试→offer→已接受` 逐态推进。
- 预期：每步成功；状态 badge 色板与 §2.1 一致；每步写 status_history（时间、A→B、来源=手动）。
- 追溯：BR-10、FR-30/31。

**TC-SM-02**（P0·正向）面试轮次子属性
- 步骤：进入面试状态后更新 `interview_round`（一面→二面）。
- 预期：不产生新状态；卡片/详情显示"面试·二面"；历史中记录轮次变更。
- 追溯：BR-10（轮次为子属性）、技设 §5。

**TC-SM-03**（P0·正向）旁路终止态进入
- 步骤：分别从 `待投递`、`笔试` 两状态，UI 拖入"已结束"列并选 `未通过`/`主动放弃`/`已过期`。
- 预期：均可进入；拖入已结束列时弹出终止态选择；卡片进入右侧折叠列。
- 追溯：BR-10、D-04。

**TC-SM-04**（P1·边界）终态重开
- 步骤：对 `未通过` 的投递，UI 重开为 `待投递`。
- 预期：仅 UI 可操作，成功并落历史；Agent/email 来源尝试重开一律 409。
- 追溯：技设 §5。

**TC-SM-05**（P1·正向）手动回退允许
- 步骤：UI 将 `面试` 回退为 `已投递`（用户知情修正）。
- 预期：成功；历史来源=手动。
- 追溯：技设 §5（UI 允许任意合法流转）。

**TC-SM-06**（P0·负例）自动来源回退拒绝
- 步骤：投递当前 `面试`；分别以 agent、email 来源写入 `笔试`、`已投递`。
- 预期：全部 409 `STATE_CONFLICT`；状态保持 `面试`；每次被拒写入落一条 `rejected` 标记的 status_history。
- 追溯：BR-11、技设 §5、AC-6 机制面。

**TC-SM-07**（P1·边界）自动来源同态幂等
- 步骤：当前 `笔试`，agent 来源重复写入 `笔试`。
- 预期：按幂等成功忽略（不产生重复历史、不报错）。
- 追溯：技设 §5。

**TC-SM-08**（P0·负例）旁路终止态的来源白名单
- 步骤：① email 来源写 `未通过`（拒信识别确认后）→ 应允许；② agent 来源写 `未通过` → 应允许；③ agent/email 来源写 `主动放弃`、`已过期` → 应 409。
- 预期：按白名单裁决；被拒落 rejected history。
- 追溯：技设 v1.1 §5（G1 建议项 1）。

**TC-SM-09**（P0·正向）AC-6 端到端：手动优先 + 用户可见提示
- 步骤：① UI 手动将投递从 `已投递` 推进到 `面试`；② 模拟邮箱识别回写 `笔试`；③ 模拟 Agent 回写 `笔试`；④ 打开 D-05。
- 预期：②③ 均不改变状态（409/忽略）；④ 摘要条显示 info 提示条"已按你的手动更新保留当前状态（BR-11），自动来源的状态 X 已被忽略"；状态历史可见两条 rejected 记录。
- 追溯：AC-6、BR-11、D-05。

**TC-SM-10**（P0·正向）状态历史完整性与来源标记
- 步骤：制造手动、邮箱识别、Agent 回写各至少一次状态变更；查看 D-05 Tab「状态历史」。
- 预期：时间线逐条含时间 + A→B + 来源标记（手动无标/邮箱识别 info 图标/Agent 回写 primary 图标）+ 备注。
- 追溯：FR-31、§2.1 来源标记规范。

**TC-SM-11**（P1·边界）看板拖拽可撤销
- 步骤：D-04 拖拽改状态后 5s 内点 toast 撤销；超过 5s 不操作。
- 预期：撤销则状态还原且不留历史（或留一对抵消记录，以实现为准记录行为）；超时后变更生效落历史。
- 追溯：D-04（G1 已拍板：拖拽即改 + 可撤销 toast）。

### 3.7 邮箱事件（AC-5，FR-40～43，BR-2，D-07/D-08/D-10）

**TC-MAIL-01**（P0·正向）IMAP 绑定
- 步骤：D-10 填写邮箱 + 授权码 →「测试连接」。
- 预期：连接成功 badge；错误授权码时即时反馈失败原因；授权码不明文回显（加密存储，技设 §2.2/§6）。
- 追溯：FR-40。

**TC-MAIL-02**（P0·正向）模拟笔试邮件识别进待确认
- 步骤：测试夹具（本地 IMAP + 模拟邮件）向绑定邮箱发一封笔试通知（含公司名、8月28日14:00、会议链接）→ 等待一个轮询周期（≤5min+余量）。
- 预期：D-07 出现该事件卡：类型 badge=笔试、解析出时间与链接、自动匹配关联投递；来源标记"邮箱识别"；原始邮件摘要可见；**未进日程**。
- 追溯：AC-5、FR-41/42、BR-2。

**TC-MAIL-03**（P0·正向）确认加入日程 + 双向关联
- 步骤：D-07「确认加入日程」→ 查 D-08 与 D-05。
- 预期：日程出现该事件（类型色 pill）；事件与投递双向可跳转；D-05「邮件回溯」可展开原始邮件摘录。
- 追溯：AC-5、FR-42/43。

**TC-MAIL-04**（P0·正向）修正后加入
- 步骤：修改解析结果（时间改 15:00、改关联岗位）后确认。
- 预期：日程事件为**修改后值**；关联到修正后的投递。
- 追溯：FR-42、AC-5。

**TC-MAIL-05**（P0·正向）丢弃即误识别反馈
- 步骤：「丢弃」→ 二次确认。
- 预期：事件从待确认移除、不进日程；误识别计数 +1（KPI-2 数据源）；原始邮件仍可追溯（不物理删除）。
- 追溯：FR-42、KPI-2、RISK-5。

**TC-MAIL-06**（P0·负例）未确认绝不入日程
- 步骤：识别出新事件后不做任何操作，遍历 D-08 各视图与 notification 列表。
- 预期：日程无任何该事件；不产生 24h/1h 提醒。策略 A 严格成立（BR-2）。
- 追溯：BR-2、OP-7。

**TC-MAIL-07**（P1·边界）重复邮件去重
- 步骤：同一封邮件被重复拉取（同 message_id）/ 内容相同的转发邮件。
- 预期：message_id 唯一约束去重；内容哈希兜底；待确认列表无重复卡。
- 追溯：技设 §6。

**TC-MAIL-08**（P1·负例）非招聘邮件不入库
- 步骤：发送广告/私人邮件。
- 预期：粗筛跳过，不产生 email_event 记录。
- 追溯：技设 §6、RISK-3 最小化留存。

**TC-MAIL-09**（P1·边界）解析不全/无法关联
- 步骤：发送缺时间或公司名无法匹配的邮件。
- 预期：仍进待确认（BR-2 一律先确认）；缺失字段可编辑；关联岗位下拉可手动选择；时间置信度有标记。
- 追溯：技设 §6、RISK-5。

**TC-MAIL-10**（P1·边界）已过期未确认沉底
- 步骤：构造事件时间已过的待确认卡。
- 预期：列表自动沉底 + warning"时间已过"；仍可确认/修正/丢弃。
- 追溯：D-07。

**TC-MAIL-11**（P1·负例）无批量确认
- 步骤：复选多条事件，检查可用批量操作。
- 预期：仅有「批量丢弃」；不存在批量确认入口（BR-2 精神：每条都值得单独过目）。
- 追溯：D-07、BR-2。

### 3.8 统计（AC-7，FR-50/51/52，§10.4，D-09）

**TC-STA-01**（P0·正向）漏斗口径对拍（10 条抽样）
- 步骤：造 10 条台账数据覆盖：待投递 2、已投递 3、笔试 2、面试 1（无笔试环节直达）、offer 1、未通过 1 → 打开 D-09，与 §10.4 手工核算对拍。
- 预期：漏斗分母不含待投递（已投递及以后 = 8）；笔试转化率 = 2/8；面试转化率 = 1/2（无笔试直达岗位不剔除，按建议稿口径）；offer 转化率 = 1/8；口径 tooltip 文案与 §10.4 一致。
- 追溯：AC-7、§10.4。

**TC-STA-02**（P0·正向）关键指标卡口径
- 步骤：同一数据集核对 D-01/D-09 四卡。
- 预期：总投递数（含待投递，按产品口径以页面说明为准）/ 进行中（非终态）/ 待确认事项数（= 待确认投递 + 待确认事件，与导航红点一致）/ offer 数；点击卡片跳转对应过滤视图。
- 追溯：FR-52、D-01。

**TC-STA-03**（P1·正向）维度筛选
- 步骤：渠道多选 + 时间段组合筛选。
- 预期：漏斗、指标卡、明细表整页联动；取消筛选恢复全量。
- 追溯：FR-51。

**TC-STA-04**（P1·空态）无数据
- 步骤：全新实例打开 D-09。
- 预期：漏斗 0 占位 + 引导录入岗位；图注说明"待投递不计入漏斗"。
- 追溯：§12、D-09。

**TC-STA-05**（P1·边界）导出 CSV（范围外增补，G1 Leader 已批准报备）
- 步骤：筛选后导出 CSV。
- 预期：CSV 内容与当前筛选的明细表一致（含状态分布列）；中文无乱码。
- 追溯：D-09（G1 记录在案的范围外微增补）。

### 3.9 邮箱授权失效（AC-8，FR-44，D-10）

**TC-AUTH-01**（P0·正向）失效提示与数据保留
- 步骤：绑定邮箱并有历史事件/日程后，使授权失效（改错授权码/服务端吊销）→ 等一个轮询周期 → 遍历各页面。
- 预期：全局顶部 danger 持续警示条"邮箱授权已失效，监控已暂停"（全页面可见、可点击直达 D-10）；该账户轮询暂停（account.status=auth_failed）；**历史已识别事件、日程、邮件回溯完整保留**；其余模块正常。
- 追溯：AC-8、FR-44。

**TC-AUTH-02**（P0·正向）恢复后续跑不重不漏
- 步骤：失效期间向邮箱发 2 封招聘邮件 → 恢复授权 → 等轮询。
- 预期：监控恢复；失效期间的 2 封被补拉识别（last_uid 续跑）；已识别过的邮件不重复进待确认。
- 追溯：FR-44、技设 §6。

**TC-AUTH-03**（P1·正向）解绑与凭据清除
- 步骤：D-10 解绑邮箱。
- 预期：监控停止；凭据清除；历史数据保留策略与产品口径一致（保留事件/日程）；再绑定需重新授权。
- 追溯：RISK-3、技设 §6。

### 3.10 空态 / 异常态 / 边界（§12，D-01～D-10 §5 矩阵）

**TC-EDGE-01**（P0·空态）无简历
- 预期：D-02 上传引导主视觉；Agent `GET /profile` 返回 200 + `{"empty": true}`（Agent 可据此提示"先完善档案"），非 404/500。

**TC-EDGE-02**（P0·空态）无投递
- 预期：D-04 居中空插画 + "还没有投递记录" + CTA + 灰显示例卡片；统计页漏斗 0 占位。
- 追溯：§12、D-04/D-09。

**TC-EDGE-03**（P0·空态）未绑定邮箱
- 预期：D-07/D-08 功能降级为提示 + 去设置 CTA（日历框架正常渲染、手动已有事件不受影响）；看板/简历/统计完全不受影响。
- 追溯：§12、D-08。

**TC-EDGE-04**（P0·空态）未配置 Agent 凭据
- 预期：D-10 签发引导 + "未配置不影响手动使用台账"说明；导航不隐藏任何功能；手动录入/看板/状态维护全可用。
- 追溯：§12、FR-25。

**TC-EDGE-05**（P0·异常）确认任务长期未处理
- 预期：持续挂起展示（>24h warning 文案），**无自动关闭**；手动关闭出口可用（同 TC-CFM-09/10，此处作 §12 场景锚点）。
- 追溯：§12、技设 v1.1 §3.4 步骤 6。

**TC-EDGE-06**（P1·边界）小屏降级
- 步骤：视口 <768px 打开应用。
- 预期：显示"请使用桌面浏览器"提示页（MVP 不做移动端）。
- 追溯：§2.3 断点、PRD §6.2。

**TC-EDGE-07**（P0·正向）两级提醒与截止提醒口径
- 步骤：① 确认的日程事件分别逼近 24h/1h；② 某岗位 deadline 进入 24h 窗口且其下无已投递及之后状态的投递；③ 修改该 job.deadline 后重查。
- 预期：① 铃铛列表 + 首页日程区倒计时各出现 24h、1h 两级应用内通知；② 截止提醒出现；③ 提醒按新 deadline 即时计算（不落库，无旧值残留）。
- 追溯：FR-32、OP-8、技设 v1.1 §4（建议项 3）。

**TC-EDGE-08**（P1·正向）提醒偏好开关
- 步骤：D-10 分别关闭 24h、1h、截止提醒开关。
- 预期：对应级别通知不再产生；开关状态持久化。
- 追溯：FR-32、D-10。

**TC-EDGE-09**（P1·异常）操作防重复提交
- 步骤：确认/保存/录入等按钮在 loading 态快速连点。
- 预期：按钮 loading 防重；服务端幂等（确认流 request_id、消息去重）兜底，不产生重复记录。
- 追溯：§5 加载态、技设 §3.4。

**TC-EDGE-10**（P1·无权限态）单用户无越权场景声明
- 预期：产品无登录/多角色 UI；所有 API 一律鉴权（FR-25），未绑定邮箱时功能降级视同空态（TC-EDGE-03 覆盖）。
- 追溯：§12 无权限态、BR-20。
